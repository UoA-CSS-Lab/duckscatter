# データ契約と数値精度

## 入力と点の対応

点は Parquet で与え、`x` と `y` に座標を持つ。URL のほか `File` / `ArrayBuffer` を受け取れる。その他の列は色・サイズ、条件、利用側の問い合わせに使う。

初期化時の準備を終えた後は、行集合、行順と点 ID の対応、座標を固定する。`onDatabaseReady` で初回描画用データを生成する前に、派生列や座標を準備することはできる。表示中に元の行や座標を変える場合は、新しい散布図を作成する（[ADR-0001](adr/0001-fixed-input-exploration.md)）。

点 ID は内部の `rowid` と GPU バッファの添字に対応し、`rowid` は `0..N-1` の連続した値であることを前提とする。利用側が持つ単語 ID や投稿 ID などの業務 ID は別の列として保持する。再読込や入力順の変更をまたいだ点 ID・選択の永続性は保証しない。

行を除外する前処理は入力 Parquet の作成時に完了させる。`onDatabaseReady` で行を `DELETE` すると初期化前でも `rowid` が疎になり、バッファ添字と一致しなくなる。初期化時の準備でも、行集合と連続した `rowid` の対応を崩さない。

ラベルは別の GeoJSON の位置付き注釈として与える。点とラベルの数や所属関係は一致を要求しない。

## 数値の前提

座標と GPU フィルター対象の値は、NULL でなく、float32 に変換した後も有限となる数値を要求する。GPU に渡す範囲条件の値も、その列と同じ単位・基準で指定する。欠損値のある行を除外する場合は入力 Parquet の作成時に行い、値を補完する場合も初回描画用データの生成前に利用側で明示的に処理する。

これは合意した入力条件であり、現在の実装が検証しているという意味ではない。現状は x/y の NULL・NaN・Infinity を明示的に検査せず、GPU フィルター列の NULL は変換により 0 になる。無効値の結果に依存した使い方は避ける。将来の検証では、無効な入力を明示的にエラーとし、行を黙って除去しない（[未対応事項](follow-ups.md#入力の検証)）。

## SQL と GPU の役割

`whereConditions` は DuckDB で評価し、GPU の数値範囲条件は列値と閾値を float32 に変換して評価する。精密な数値比較が必要な場合は SQL 条件を使う。SQL 自体の判定精度は元データの列型と式に従う。

例えば epoch ミリ秒の `1_700_000_000_000` と、その 1 秒後の値は同じ float32 値になる。日時のスライダーなどに GPU 条件を使う場合は、基準時刻からの差分を適切な単位で持つ列を用意し、条件にも同じ基準を使う。必要な範囲と分解能を満たせるか確認する。

現在の CPU ホバーは float32 にした列値と、丸める前の JavaScript の範囲条件を比較する。そのため、近似を前提としても CPU と GPU で判定がずれる不整合が残る。例として値 `16_777_216`、下限 `16_777_217` では、GPU では下限も丸められて一致し、CPU ホバーでは一致しない。この不整合は許容する仕様として扱わず、[修正対象](follow-ups.md#cpu-と-gpu-の範囲判定)とする。

## 問い合わせと件数

`runQuery()` へ渡す SQL に、表示中のフィルター・選択・表示範囲・LOD の条件は自動適用しない。`SELECT COUNT(*) FROM parquet_data` は全件数を返す。集計や一覧を現在の絞り込みに合わせる場合は、利用側が対応する条件をクエリに指定する。

`getSelectionCount()` は選択集合の全件数であり、表示中の選択点数ではない。`getFrameStats().drawnCount` は描画された一致点の取得値で、灰色の不一致点を含まず、全描画点数とも異なる。意味は [用語集](../CONTEXT.md)、計測の限界は [開発手順](development.md) を参照。
